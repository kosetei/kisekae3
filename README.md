# kisekae3 — 実物写真ベースの着せ替えアプリ

キャラと服の画像を組み合わせ、初回はComfyUIで画像を生成し、生成済みなら表示するアプリです。

## 実行

```
npm start        # サーバーを起動。server.js と依存モジュールの変更時は自動再起動
#                # → http://localhost:3000
npm run start:no-watch # watchなしでサーバーを起動
#                # → http://localhost:3000
```

VS Codeでは「タスク: タスクの実行」から「サーバー起動 (watchあり)」または「サーバー起動 (watchなし)」を選べます。

画面ファイルの変更はサーバー再起動なしで反映されます。ブラウザーを再読み込みしてください。

LAN内の別端末からは、起動時に表示される `kisekae3 network` のURLへ接続してください。
Windowsファイアウォールで許可を求められた場合は、プライベートネットワークでのアクセスを許可してください。
このアプリには認証がないため、インターネットへ直接公開しないでください。

依存パッケージなし（Node 18+ の標準機能のみ）。

## データ構成（すべてフォルダの中身から自動でカタログ化）

```
store/
  characters/<charId>.(png|jpg|jpeg|webp|gif|svg|heic|heif)        ← キャラ（後から追加すれば候補に出る）
  characters/<charId>/icon.(png|jpg|jpeg|webp|gif|svg|heic|heif)   ← 従来のフォルダ形式も利用可能
  clothes/<dressId>.<ext>                                 ← 服（後から追加すれば候補に出る）
  generated/<charId>/<dressId>.<ext>                     ← 既存の生成結果（手動生成済み分もここ）
  generated/<charId>/<dressId>__<日時>-<ID>.<ext>         ← 再生成したバージョン
```

- キャラ名/服名はファイル名（拡張子を除く部分）がそのまま使われます。
- 既存の `images/` は参考用としてアプリからは読みません（data.js は削除済み）。

## 動作

キャラ一覧・服一覧・着せ替え画面ではフォルダをアイコンと名前で先頭に並べ、クリックすると中身を表示します。整理画面でフォルダを開くと、フォルダ名を変更できます。初期表示では「未分類」を開きます。整理画面も同じフォルダ表示で、画像または画像左上のチェックボックスをクリックして複数選択できます。選択項目のつまみを目的のフォルダアイコンへドラッグするとまとめて振り分けられます。「フォルダを作成」で新しいグループを追加できます。フォルダ分けはアプリ内の表示分類で、画像ファイル自体は移動しません。情報は `store/catalog-metadata.json` に保存されます。キャラ一覧の「キャラ・服を追加」から画像を選んで追加でき、IDは既存と重複しない `charaN` / `dN` を自動で割り当てます。複数画像を選択すると一括追加し、個別の失敗があっても残りは続けて追加します。PNG / JPEG / WebP / GIF / HEIC / HEIF（1枚8 MB以下）を受け付けます。HEIF画像は変換せずに保存し、ComfyUIへそのまま送信します。

服の編集で複数画像を選択し「選択した服をバリエーションとしてまとめる」と、着せ替え画面では1着として表示されます。選択した服の画像バリエーションを解除することもできます。バリエーションをまとめた服を選ぶと、生成に使う画像をサムネイルから選択できます。選択画像は生成・再生成に使われ、生成履歴と服用プロンプトは同じ服として共有されます。生成画像は使用した服画像のIDで記録されるため、バリエーション化前の既存履歴は統合後も表示され、解除後は元の服画像ごとの履歴に戻ります。

キャラ選択画面では、フォルダ内のキャラを登録順・生成数が多い順・最近生成した順に並べ替えられます。初期表示は生成数が多い順です。キャラは1ページ30件ずつ表示されます。フォルダ一覧の最後の「ランダム」を選ぶと、全フォルダから最大6人を抽選して表示します。再度選ぶと抽選し直します。サムネイルは「余白なし」または「全体を表示」から選べ、初期表示は全体表示です。設定はブラウザーに保存されます。

キャラ画面の服一覧には「表示する服」の切り替えがあります: 自動 / すべて / 生成済みだけ / 未生成だけ。選択はブラウザーに保存され、初期表示は「自動」です。「自動」はヘッダーの状態確認（アクセス時と画面遷移時）の結果を使い、ComfyUI が応答すれば（`GENERATOR=mock` を含む）すべて、応答しなければ生成済みだけを表示し、「自動: ComfyUI 応答なし → 生成済みだけ（2件）」のように理由を表示します。確認が終わるまでは前回の状態（ブラウザーに保存）で表示し、前回の状態がなければすべてを表示します。ほかの値を選んだ場合は、「自動」を選び直すまでその選択を使います。ComfyUI が応答しないときは「この服を生成」「未生成を一括生成」「選択中を再生成」を理由つきで無効にします。生成済み画像の表示・履歴・バージョン切り替えはそのまま使えます。件数（表示件数・フォルダ内件数・生成済み件数）も同じ行に表示します。選択中の服は条件に当てはまらない場合でも一覧に残し、ステージの表示とズレないようにします。この表示条件欄は、縦画面では服グリッドの下（フォルダの下）に回し、画像と服の選択肢を近づけます。横向きのサイドバーレイアウトでは上部に残します。

キャラ一覧 → キャラ画面 → 服を選ぶと:

1. `store/generated/<char>/<dress>` にファイルがあればそれを表示
2. なければ生成設定が開きます。プロンプトを確認・選択・編集して「この服を生成」を押すか、選択中の服をもう一度クリック（タップ）すると生成します（「未生成を一括生成」は従来どおり未生成の服を続けて生成します）。UIは4秒ごとに再スキャンするので、手動で画像を置いても次回リフレッシュで「生成済み」になります。
3. プロンプトは「キャラ調整用」と「服の」プロンプトに分けて保存できます。キャラ向けの入力は初期状態では空欄で、保存済み・最後の生成・プリセットを選択するか入力した場合にだけ生成へ追加されます。服向けの入力は服ごとに保存して他のキャラに再利用しにくくなります。生成時には両方を結合して送信し、履歴には結合したプロンプトと各入力欄の内容を別々に保存します。服欄ではデフォルトプロンプト・用途別プリセット・最後の生成プロンプト・保存済みプロンプト・共通の入力を引き継ぐ設定を選べます。デフォルトプロンプトを選ぶと、ワークフローの既定プロンプトを服欄へ戻せます。初回など再利用できる服プロンプトがない場合は、現在の入力を引き継ぎます。プリセットはキャラ用と服用を別々に保存し、それぞれの入力欄から選択します。以前の形式のプリセットは服用として扱います。未保存の編集が移動や切り替えで失われる場合は、そのキャラ用または服用に保存するか確認します。シード欄の「ランダム」ボタンで新しいシードに変更できます。生成済みの服は「選択中を再生成」で新しいバージョンを追加します。複数ある場合は画像下の選択欄から表示を切り替えられます。「生成画像を整理」では履歴を一覧し、画像ごとの「設定を見る」から生成時のキャラ用・服用プロンプト、シード・LoRA設定を個別に確認し、モーダル内のボタンで入力欄へ適用できます。今後の生成設定は `store/generated-metadata.json` に保存されます。分割対応前の画像は個別プロンプトが記録されていないため、結合済みプロンプトを服用欄に表示します。画像の「サムネ」ボタンで第一選択を変更でき、次回以降もその服の初期表示に使われます。

API:

- `GET /api/catalog` — キャラ・服・生成済みマップ
- `POST /api/catalog-group {type, group}` — キャラまたは服のフォルダを作成
- `PUT /api/catalog-group {type, group, newGroup}` — フォルダ名を変更
- `DELETE /api/catalog-group {type, group}` — フォルダを削除して中のアイテムを未分類へ移動
- `GET /api/config` — ワークフローJSONに設定された既定プロンプト
- `GET /api/prompt-settings` / `PUT /api/prompt-settings` — プロンプトプリセットとキャラごとの設定・服ごとの設定（`store/prompt-settings.json` に保存）
- `PUT /api/generated-selection {character, dress, file}` — その服の第一選択画像を保存（`store/generated-preferences.json`）
- `GET /api/generated-settings?character=...&dress=...&file=...` — 生成画像の結合プロンプトと個別入力、シードを取得
- `DELETE /api/generated-image {character, dress, file}` — 生成画像を削除
- `POST /api/upload {type, image, alias?}` — キャラまたは服画像を追加（IDは自動採番、`image` はBase64 data URL）
- `PUT /api/catalog-item {type, id, alias, group}` — カタログ項目の表示名とフォルダ名を保存
- `PUT /api/catalog-items {type, items: [{id, alias}], group}` — 複数項目を同じフォルダへ一括移動
- `PUT /api/clothing-variants {ids, outfitId}` — 複数の服画像を1着にまとめる（`outfitId` は選択した画像ID）、または `outfitId: null` でバリエーションを解除
- `POST /api/generate {character, dress, dressVariant, prompt, characterPrompt, dressPrompt, seed, force, disableLora}` — `dressVariant` は同じ服にまとめた画像のID（省略時は服の代表画像）。`characterPrompt` と `dressPrompt` を指定すると結合して生成し、履歴には各入力も個別に記録（`prompt` のみの従来リクエストも引き続き利用可能）。既存なら `{status:"existing"}`, なければ生成。`seed` は省略可能な0以上の安全な整数。`force: true` は既存結果を残したまま新しいバージョンを生成。`disableLora: true` はワークフロー内のLoRAローダーをバイパスして生成（省略時はワークフロー設定どおり）

## ComfyUI

ComfyUIを起動し、ワークフローが参照するモデルとカスタムノードをインストールしてください。
既定ではルートの `image_flux2_klein_image_edit_9b_distilled.json` を読み込みます。
ワークフロー内のサブグラフをComfyUI API形式に展開し、キャラ画像・服画像を入力して実行します。
生成画像は `store/generated/<char>/<dress>__<日時>-<ID>.png` に保存され、以前の画像も残ります。従来の `<dress>.<ext>` 形式の画像も引き続き表示されます。

- `COMFYUI_URL` — ComfyUI URL（既定値 `http://127.0.0.1:8188`）
- `SERVER_CHECK_PORT` — ComfyUI が動く PC の起動確認に使う TCP ポート（既定値 `3389` = RDP、数値でない場合は既定値に戻ります）。ヘッダーの状態表示で使用し、アクセス時と画面遷移時にのみ確認します
- `WOL_MAC` — ComfyUI が動く PC の MAC アドレス。設定すると、PC 停止中の表示の横に Wake on LAN の「起動」ボタンが出ます（ブロードキャストはルーターを越えないため、kisekae3 と同じサブネットセグメント上の PC のみに効果あり。`/api/wake` は認証なしで、同じ LAN 上のユーザーなら誰でも送信できます）
- `WOL_BROADCAST` — マジックパケットの送信先（既定値 `255.255.255.255`）
- `WOL_PORT` — マジックパケットの送信ポート（既定値 `9`）
- `COMFYUI_WORKFLOW` — 別のワークフローJSONを使う場合のファイルパス
- `GENERATOR=mock` — ComfyUIを使わずプレースホルダー画像を生成する開発用モード

これらの環境変数は、プロジェクトルートの `.env` に記入すると `npm start` 時に自動で読み込まれます。
`.env.example` を参考に設定してください。`.env` はローカル設定としてGit管理されません。

ComfyUIへの接続確立は3秒でタイムアウトします。接続後の画像アップロードや生成完了待ちには、この制限は適用されません。
生成はComfyUIが完了するまで待機します。

ComfyUIが起動していない、モデルが不足している、またはワークフローに問題がある場合は、
画面に生成エラーが表示されます。

### ComfyUI のオンデマンド起動（任意）

`COMFYUI_START_TASK` を設定すると、ComfyUI が止まっているときにアプリから起動できます。ヘッダーに「ComfyUI を起動」ボタンが出るほか、停止中に生成ボタンを押すと「ComfyUI を起動しますか？」と確認します。起動が終わっても生成は自動では始まらないので、もう一度生成ボタンを押してください。

起動は `POST /api/comfyui/ensure` で、次の順に進みます。

1. ComfyUI の `/system_stats` が応答すれば何もしない
2. PC が応答しない（`SERVER_CHECK_PORT`）ときは Wake on LAN を送り、PC の起動を待つ（`WOL_MAC` が必要）
3. PC が起動していて ComfyUI が応答しないときは、`ssh <COMFYUI_SSH_USER>@<COMFYUI_URL のホスト> schtasks /Run /TN <COMFYUI_START_TASK>` でタスク スケジューラのタスクを実行する。`COMFYUI_KEEP_AWAKE_TASK` があれば、その直前にスリープ防止タスクも同じ方法で実行する
4. `/system_stats` が応答するまで待つ

起動処理はサーバー側のジョブとして動き、API はすぐに返ります。進み具合は `GET /api/comfyui/ensure` で確認できます。起動処理中は `/api/server-status` が `starting: true` を返し、画面では「ComfyUI 起動中」と表示されます。服フィルタの「自動」は「生成済みだけ」になり、生成ボタンは無効になります。状態の確認は通常、アクセス時と画面遷移時だけです。ただし、そのタブで起動を始めたときだけは、起動が終わるまで5秒ごとに進み具合を確認します。

- `COMFYUI_START_TASK` — 実行するタスク名（例: `start_comfy`）。未設定なら起動機能は無効です。英数字と `_ . -` のみ使えます
- `COMFYUI_SSH_USER` — PC へ SSH で接続するユーザー（例: `tatei`）。英数字と `_ . -` のみ使えます。接続先は常に `COMFYUI_URL` のホストです
- `AUTO_START` — `1` にすると、`/api/generate` は ComfyUI が止まっていれば起動を待ってから生成します（既定値 `0`。既定では画面の確認ダイアログを経由します）
- `COMFYUI_WAKE_TIMEOUT_MS` — WOL 後に PC の起動を待つ時間（既定値 `180000` = 180秒。休止状態からの復帰は時間がかかるため長めにしています）
- `COMFYUI_START_TIMEOUT_MS` — タスク実行後に ComfyUI の応答を待つ時間（既定値 `180000` = 180秒。モデルの読み込み時間を見込んでいます）
- `COMFYUI_POLL_INTERVAL_MS` — 待機中に確認する間隔（既定値 `5000`）
- `COMFYUI_RESUME_GRACE_MS` — WOL で PC が起動したあと、すでに動いている ComfyUI が応答するのを待つ時間（既定値 `15000`）。スリープからの復帰では ComfyUI がそのまま動いていることがあるため、二重起動を避けるために少し待ちます
- `COMFYUI_START_MIN_INTERVAL_MS` — `schtasks /Run` を送る最低間隔（既定値 `120000` = 2分）。間隔内にもう一度呼ばれたときは、起動コマンドを送らずに応答を待ちます
- `COMFYUI_VRAM_GUARD_MB` — 設定すると、起動前に `nvidia-smi` で GPU のメモリ使用量を確認し、この値（MB）を超えていれば起動を保留します。画面で確認すると、そのまま起動できます（`{"force": true}`）。未設定なら確認しません
- `COMFYUI_KEEP_AWAKE_TASK` — スリープ防止タスクの名前（例: `keep_awake`）。英数字と `_ . -` のみ使えます。設定すると、ComfyUI の起動タスクを実行するときにこのタスクも実行します。画面から起動を要求したときは、ComfyUI がすでに動いていても実行します。2分（`COMFYUI_START_MIN_INTERVAL_MS`）に1回までで、失敗しても起動処理は失敗にせず、注意として表示します。未設定なら実行しません
- `COMFYUI_SSH_BIN` — 使う ssh コマンド（既定値 `ssh`。主にテスト用）

前提と注意:

- **タスクは対話セッションで動かす必要があります。** タスクは「ユーザーがログオンしているときのみ実行する（Interactive only）」で、ComfyUI を使うユーザーとして登録してください。サービス（システム）として実行すると、環境変数（home / cache）の違いでモデルや画像の読み込みに失敗します。そのユーザーがログオンしていないと `/Run` は失敗します。スリープ・休止状態からの復帰ではログオンセッションが残るので動きます（休止状態からの復帰は時間がかかります）。再起動やシャットダウンのあとは、一度ログオンが必要です。
- **SSH は鍵認証で、パスワードなしで通る必要があります。** `BatchMode=yes`（パスワードを聞かない）と `ConnectTimeout=5` で実行します。raspi2 では、kisekae3 を動かすユーザー（`kisekae3.service` の `User=`）から `<COMFYUI_SSH_USER>@<host>` へ鍵認証で通る必要があります。サービスのユーザーが鍵を持っていなければ、そのユーザーの公開鍵を PC 側の `authorized_keys` に追加してください。そのユーザーで `ssh -o BatchMode=yes -o ConnectTimeout=5 <user>@<host> "schtasks /Query /TN <task>"` が通ることを確認してください。
- **起動タスク（`start_comfy.bat`）は、自分で二重起動を防ぐ必要があります。** ComfyUI が起動しているかは `/system_stats` だけで判断し、タスクの Status（Running）は使いません。`/Run` は待機中にも送る可能性があるので、bat の先頭で `netstat -ano | findstr ":8188" | findstr "LISTENING" >nul && exit /b 0` のように、すでに待ち受けていれば何もせずに終わるようにしてください。アプリ側でも、同時の起動要求は1つにまとめ、`/Run` は最低2分あけて送ります。
- タスク スケジューラの「タスクが既に実行中の場合に適用される規則」（MultipleInstancesPolicy）は、`start_comfy` も `keep_awake` も「新しいインスタンスを開始しない」をおすすめします。
- スリープ防止タスクの登録例（管理者権限が必要）。スクリプト側にも単一インスタンスのガードを入れてください。

  ```
  schtasks /Create /TN keep_awake /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\tatei\comfy-keep-awake.ps1" /SC ONCE /RU tatei /RL LIMITED /F
  ```

  `schtasks` ではトリガーなし（On demand）で作れないため、`/SC ONCE` で登録して `/Run` で呼び出します。
- タスク名・ユーザー・ホストは環境変数の固定値だけを使います。リクエストからは受け取らず、ssh はシェルを通さずに実行します。ただし、このアプリには認証がないため、同じ LAN 上のユーザーなら誰でも起動を要求できます。
